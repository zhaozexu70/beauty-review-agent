## 1. 一分钟项目介绍（可以直接说）

> 我做了一个“个护美妆评论洞察 Agent”。用的是公开的中文电商评论数据集，选了洗发水品类，清洗后约一万条。
>
> 它做四件事：第一，用大模型把评论分成正向/中性/负向，并从 13 个固定的问题标签里选 1–2 个，比如“真伪”“包装”“头皮刺激”；第二，用代码统计各类问题的占比和典型原话；第三，回答成分、头皮类型、售后规则这类问题时，先检索知识库，并标出出处，查不到就说查不到；第四，自动生成给品牌方的改进报告。
>
> 我花最多精力的是评测。我固定了 300 条带人工标签的评论，第一版 prompt 准确率 90.33%。我逐条看了 29 个错误，发现 28 个都是模型判成了“中性”，比如“还没用，等用了再评价”，而这个数据集的标签其实反映的是买家的整体满意度，这种评论通常是好评。我据此改了第二版 prompt，准确率到了 98%。但因为第二版是看着这些错误写的，可能有点“背答案”，所以我又拿了另外 300 条从没看过的评论来验证，提升到 95.67%，这个才是更可信的数字。
>
> 这个过程就是一个小的数据飞轮：发现 badcase → 归因 → 改 prompt → 重新评测。

## 2. 整体流程（画给面试官听）

```
评论 CSV
  └─> load_reviews（加载）
        └─> classify_reviews（大模型分类：每 20 条一批，输出 JSON，pydantic 校验，不合格重问一次）
              └─> aggregate_stats（pandas 统计：占比、Top 负向问题、原话）
                    └─> write_report（数字由代码填，文字由大模型写）
问题 ──> search_kb（TF-IDF 检索知识库，返回段落 + 文件名）──> 带出处的回答
```

Agent 的“大脑”就是一个循环（`src/agent.py`，99 行）：
1. 把对话和 5 个工具的说明发给大模型；
2. 大模型如果说“我要调用某个工具，参数是……”，代码就去执行这个工具，把结果再发回给大模型；
3. 大模型如果直接给出回答，就结束。最多 8 步，防止死循环。

## 3. 每个设计为什么这么做

### 3.1 为什么用 tool calling（工具调用），而且不用 LangChain 之类的框架？
- **大模型擅长理解语言，不擅长算数和记数据。** 统计占比交给 pandas，检索交给 TF-IDF，大模型只负责“决定下一步做什么”和“把结果说成人话”。这样数字不会被模型编出来。
- **不用框架是为了透明。** 循环只有几十行，每一步调用了什么工具、传了什么参数、返回了什么，App 里都能展开看到，也能写单元测试（`tests/test_agent_loop.py`）。面试或排查问题时，能说清楚每一步发生了什么。

### 3.2 为什么用固定的标签体系？
- 如果让模型自由写标签，今天写“掉发”，明天写“脱发”，后天写“头发掉得多”，**没法统计，也没法按月对比**。
- 固定 13 个标签，并用 pydantic 校验：标签不在列表里、超过 2 个、漏了某条评论，都会被拦下来并重问一次。
- 真实效果：v1 有 6 条评论给了 3 个标签，被拦下后重问一次全部修正，最终 JSON 失败率是 0。

### 3.3 为什么用 TF-IDF，而不是 embedding（向量检索）？
- 知识库很小（3 个文件、16 个段落），TF-IDF 已经够用。
- **零成本、可解释、不用额外模型**：能看到是哪些字重合导致命中的。
- 中文没有空格，我用“字符 n-gram”（1–3 个字一组），不需要分词工具。
- 我也看到了它的缺点：用户说“假货”，知识库写的是“真伪/正品”，一开始匹配不上。我的处理是在知识库里补上用户常用说法。知识库变大以后，下一步会换成 embedding 或混合检索。
- 还设置了一个最低相似度阈值（0.12），低于它就当作“知识库没有答案”，比如问“今天股票涨了吗”会返回空。

### 3.4 为什么 temperature 设为 0？
- 分类任务要的是**稳定、可复现**，不是创意。temperature=0 让模型尽量每次都选概率最高的答案。
- 但 temperature=0 **不等于完全一样**，所以我专门测了稳定性：关掉缓存跑两遍，v2 有 94.67% 的评论情感和标签完全一致，情感单独看是 99.67% 一致，不一致主要来自“要不要加第二个标签”。

### 3.5 为什么要做磁盘缓存？
- 缓存的 key 是（prompt 版本、模型、输入内容）。同样的输入再跑一次，直接读缓存，**不花钱、秒出结果**。
- 换了 prompt 版本，key 就变了，自然会重新调用，不会拿旧结果冒充新结果。
- 额外好处：把缓存一起提交到 GitHub，别人**没有 API Key 也能打开 App 看完整演示**（演示模式）。

### 3.6 评测为什么这样设计？
- **固定评测集**（300 条，正负各半，random_state=42）：每次改 prompt 都在同一批数据上比较，才公平。
- **中性算错**：数据只有正/负两种人工标签，模型说“中性”无法和标签对上，所以算错，并单独报告“中性率”，让问题看得见。
- **Macro-F1**：正负两类分别算 F1 再平均，避免模型只擅长一类也能拿高分。
- **混淆矩阵**：一眼看出错在哪，比如 v1 有 22 条正向被判成中性。
- **JSON 失败率**：线上跑的时候，格式不合格也是一种失败。
- **稳定性**：同一输入跑两次结果不一样，业务上就不可信。
- **Holdout 集**：v2 是看着评测集的错误写的，可能“背答案”，所以用另外 300 条没看过的数据验证。评测集提升 7.67 个百分点，holdout 提升 5.67 个百分点，差的那部分就是“背答案”带来的乐观。
- **标签不报准确率**：标签没有人工标准答案，我不能编一个准确率。我准备了 50 条待人工标注的表，标完后用脚本算一致率。

## 4. 和“数据飞轮”的关系

数据飞轮就是：**用起来 → 收集问题 → 改进 → 再评测 → 更好用 → 收集更多问题……**

在这个项目里，我真实跑了一圈：

| 步骤 | 我做了什么 | 证据 |
|---|---|---|
| 1. 跑基线 | prompt v1 在 300 条上评测：90.33% | `outputs/eval_results/v1/metrics.json` |
| 2. 收集 badcase | 导出 29 个错误 | `outputs/eval_results/v1/badcases.csv` |
| 3. 归因 | 人工归成 4 类：A 未使用/待追评（17）、B 夸产品骂平台（5）、C 小保留但接受（4）、D 标签有歧义（3） | `badcase_categories.csv` |
| 4. 修复 | 写 v2：重新定义情感 = 整体满意度，加规则和例子 | `src/prompts.py` |
| 5. 再评测 | 评测集 98.00%，holdout 95.67% | `outputs/eval_results/v2/`、`holdout/` |
| 6. 发现新问题 | v2 修好 26 个，新错 3 个（长评论里抱怨的是别的事） | `docs/prompt_iteration.md` |
| 7. 下一圈 | v3 方向：区分“这一单”和“别的事”；建 dev 集 | 同上 |

放到真实业务里：评论分析结果给运营看 → 运营标出“这条分错了” → 进入 badcase 池 → 定期改 prompt 或标签体系 → 在固定评测集上回归测试，指标不降才上线。

## 5. 12 个可能被问到的问题

**Q1：为什么要用大模型？传统的情感分类模型不行吗？**
答：传统模型（比如 BERT 微调）在情感二分类上也能做得很好，但需要标注数据和训练。这个场景还要同时打问题标签、写报告、回答问题，大模型一个 prompt 就能做，冷启动快。如果量很大、成本敏感，可以用大模型先标一批数据，再训练一个小模型来跑全量，这也是常见做法。

**Q2：98% 准确率是不是很高了？可以直接上线吗？**
答：要谨慎。第一，98% 是在我看过错误后调出来的评测集上，holdout 上是 95.67%；第二，评测集只有 300 条，一条就是 0.33 个百分点；第三，这只是情感，标签还没有人工验证。上线前我会扩大评测集、完成标签标注，并持续监控。

**Q3：为什么 v1 那么多“中性”？**
答：因为 v1 只说了“判断情感”，没定义情感是什么。模型把“还没用，等追评”理解成没有情绪 = 中性。但这个数据集的标签反映的是买家整体是否满意，这类评论一般是好评。根本原因是**任务定义和数据标签口径不一致**，不是模型能力问题。v1 只要给出了正/负判断，准确率是 99.63%。

**Q4：v2 有没有变差的地方？**
答：有三点。① 修好 26 个错误，同时新弄错了 3 个：都是长评论，对这次购买满意，但顺带骂了别的商家或别的平台，被 v2 的“有抱怨就判负”规则误伤；② 非中性样本上的准确率从 99.63% 降到 98.66%；③ 稳定性从 95.67% 降到 94.67%，没有变好。

**Q5：怎么防止大模型编数字？**
答：三层。① 数字全部由 pandas 统计，报告里的数量、占比、原话都是代码填进去的；② 让大模型写建议时，只给它统计结果的 JSON，并要求只能使用里面的数字；③ 我抽查过 Agent 的回答，比如“真伪 54 条，占负向 35.5%”，和工具返回的结果一致。

**Q6：知识库里没有答案时怎么办？**
答：检索相似度低于阈值时，工具直接返回“知识库中没有找到相关内容，请如实告诉用户”，系统 prompt 也要求这种情况必须说“知识库中没有相关信息”。实测问“这款洗发水能治脱发吗”，Agent 回答知识库没有相关信息，并说明不能提供医疗建议。

**Q7：tool calling 具体是怎么工作的？**
答：我把 5 个工具的名字、用途、参数格式（JSON Schema）发给模型。模型如果觉得需要某个工具，会返回一个“调用请求”，比如 `search_kb(query="漏液")`。我的代码执行这个函数，把结果作为一条 `tool` 消息发回去，模型再决定下一步，直到它给出最终回答。

**Q8：为什么每批 20 条？**
答：一条一条调用太慢、太贵（每次都要重复发 prompt）；一次发太多，模型容易漏条或格式出错。20 条是折中。我还会校验每批返回的 id 是否齐全，漏了就重问。

**Q9：稳定性 94.67% 是什么意思？怎么提高？**
答：同一个 prompt、同样 300 条评论，关掉缓存跑两次，94.67% 的评论情感和标签完全一样。情感几乎完全稳定（99.67%），主要是标签在“要不要加第二个”上摇摆。提高的办法：写清楚什么时候加第二个标签；或者只用第一个标签做统计；或者跑多次取多数。

**Q10：花了多少钱？大规模跑要多少钱？**
答：全部实验 116 次调用，约 ¥0.42（按假设单价估算，请以官网为准）。评测 300 条一次：v1 约 ¥0.055，v2 约 ¥0.078（v2 的 prompt 更长、多输出一个 reason）。按比例线性外推，1 万条评论用 v2 大约 ¥2.6（这是推算，不是实测）。缓存保证重复运行不花钱。

**Q11：如果要用到公司真实业务，你会怎么改？**
答：① 接入真实评论，加商品 ID、时间字段，做分 SKU、按周趋势和异常预警；② 和业务一起定标签体系，并按品类扩展；③ 建人工抽检机制，badcase 回流；④ 知识库换成公司真实的成分说明和售后规则，并由合规审核；⑤ 检索升级到 embedding，并建检索评测集。

**Q12：这个项目里你觉得最大的收获是什么？**
答：**先定义清楚“对”是什么，再去优化。** v1 到 v2 最大的提升不是靠更花哨的技巧，而是发现“情感”的定义和数据标签口径不一致。另外，评测要防止自己骗自己，所以我加了 holdout 集，并如实写出了 v2 的退步和局限。

## 6. 诚实的局限（主动说出来是加分项）

1. **只有一个品类**（洗发水），而且是公开语料，没有商品、品牌、时间信息。
2. **标签是二分类**，没有“中性”金标准；问题标签完全没有金标准，所以没有报告标签准确率。
3. **数据是人为平衡的**（正负各一半），报告里的差评占比不代表真实店铺的差评率。
4. **知识库是演示内容**，只有 3 个文件，是我写的通用科普和虚构的示例售后政策，不代表任何真实品牌或平台。
5. 评测集只有 300 条，样本量小；v2 对评测集有一定过拟合（holdout 提升更小）。
6. 问答助手没有多轮记忆；花费是按假设单价估算的。
